## Scope

Defines how multiple Oh My Docs handbooks share one user-owned Supabase
project without sharing physical table DDL. Extends
`SPEC-supabase-content-source-contract` and is enforced by
`SPEC-supabase-content-port`.

## Interface

```json
{
  "contentSource": {
    "ssot": "supabase",
    "supabase": {
      "projectRef": "abcdefghijklmnopqrst",
      "handbookId": "skills-docs",
      "schemaVersion": "1.1"
    }
  }
}
```

| Field | Rules |
|---|---|
| `projectRef` | Linked Supabase project; unchanged meaning from SPEC-010 |
| `handbookId` | Stable slug unique within `projectRef`; `[a-z][a-z0-9-]{1,62}` |
| `schemaVersion` | Bundled migration set expected **for this handbook only** |

`pgSchema` is derived as `omd_h_` + `handbookId` with `-` → `_`. It is stored
in the registry; clients may recompute it but must not invent a different
mapping.

## Behavior

### Registry

`public.omd_handbooks` holds one row per handbook:

| Column | Meaning |
|---|---|
| `handbook_id` | Primary key; matches contract `handbookId` |
| `pg_schema` | Postgres schema name (`omd_h_…`) |
| `schema_version` | Last successfully applied schema version |
| `created_at` / `updated_at` | Timestamps |

Provision is idempotent on `handbook_id`. Creating a handbook creates the
Postgres schema and applies the migration set for the requested
`schemaVersion` into that schema only.

### Content tables

Inside each handbook schema:

- `omd_documents` — same columns as schema `1.0` unless a later handbook
  `schemaVersion` adds columns for that schema alone
- `omd_catalog_meta` — same catalog registration shape as today

Queries always qualify `{pg_schema}.omd_documents` (or set a transaction
`search_path` to that schema). Cross-schema joins for product features are
out of scope.

### Schema evolution

1. New DDL ships as a new bundled `schemaVersion` (for example `1.1`, `1.2`).
2. Apply runs against **one** `handbookId`’s `pg_schema`.
3. Sibling handbooks keep their previous `schema_version` until migrated.
4. Runtime `schema_drift` compares live digest of the selected handbook’s
   schema to the contract’s `schemaVersion`.
5. Breaking changes require an explicit per-handbook migrate; there is no
   project-wide forced upgrade.

Optional product columns that vary without DDL should prefer `frontmatter`
jsonb over additive tables when possible, so most handbooks stay on a small
set of schema versions.

### Legacy `1.0` layout

If `public.omd_documents` exists and `public.omd_handbooks` does not:

- Treat the project as a single handbook with `handbookId: "default"` and
  `pg_schema: public`.
- Reads/writes continue against `public.omd_*`.
- An explicit migrate creates a registry row, creates `omd_h_default` (or a
  chosen id), moves tables/data, and updates contracts.

Missing `handbookId` on a multi-handbook project (registry present) is an
error. On a legacy single-handbook project, omitted `handbookId` defaults to
`"default"`.

## Data and invariants

- One repository ↔ one `(projectRef, handbookId)`.
- `handbook_id` unique per Supabase project; `pg_schema` unique.
- No document row is visible to another handbook’s port operations.
- RLS remains enabled on content tables; policies are created inside each
  handbook schema. Registry writes require authenticated (or service) role;
  anon may read registry only if the docs app needs it to resolve
  `pg_schema` (optional—clients may derive `pg_schema` without reading the
  registry).
- Credentials never enter `.omd` JSON.

## Errors

| Code | When |
|---|---|
| `handbook_id_required` | Registry exists but contract omits `handbookId` |
| `handbook_id_invalid` | Slug fails format or is reserved |
| `handbook_id_conflict` | Registry row exists with a different `pg_schema` mapping |
| `schema_drift` | Selected handbook’s live schema ≠ contract `schemaVersion` |
| `legacy_layout_ambiguous` | Both `public.omd_*` content and a conflicting registry entry |
| `project_inaccessible` | Host cannot access `projectRef` |

## Compatibility

- Single-handbook `schemaVersion` `1.0` projects keep working.
- `local` and `notion` contracts are unchanged.
- Does not introduce Oh My Docs–hosted tenancy.

## Acceptance criteria

- Two `handbookId`s on one `projectRef` store disjoint document sets.
- Migrating handbook A’s schema leaves handbook B’s `schema_version` and
  `check` result unchanged.
- Legacy `public.omd_*` projects resolve as `handbookId: "default"`.
- Contract round-trip includes `handbookId` without secrets.
