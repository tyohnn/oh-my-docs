> **Superseded by `ADR-008` / `PRD-008`.** Multi-handbook Supabase tenancy is
> not shipping. Kept for history.

## Scope

Defines how multiple Oh My Docs handbooks share one user-owned Supabase
project without sharing physical table DDL, and how the **skill** owns a
forward migration chain for Oh My Docs platform objects. Extends
`SPEC-supabase-content-source-contract` and is enforced by
`SPEC-supabase-content-port`.

## Interface

```json
{
  "contentSource": {
    "ssot": "supabase",
    "supabase": {
      "projectRef": "abcdefghijklmnopqrst",
      "handbookId": "skills-docs",
      "schemaVersion": "1.1"
    }
  }
}
```

| Field | Rules |
|---|---|
| `projectRef` | Linked Supabase project; unchanged meaning from SPEC-010 |
| `handbookId` | Stable slug unique within `projectRef`; `[a-z][a-z0-9-]{1,62}` |
| `schemaVersion` | Bundled migration set expected **for this handbook only** |

`pgSchema` is derived as `omd_h_` + `handbookId` with `-` → `_`. It is stored
in the registry; clients may recompute it but must not invent a different
mapping.

## Behavior

### Shared Supabase project vs per-handbook Vercel

| Layer | Unit |
|---|---|
| Supabase project `oh-my-docs` | Shared BYO database (many handbooks) |
| Git repo + Vercel project `{projectSlug}-omd` | One handbook / one deployable docs app |

`oh-my-docs` is a **Supabase** display name only. Vercel deploys are
**per handbook repository**, not one Vercel named oh-my-docs.

**Vercel project name** is `{projectSlug}-omd`, where `projectSlug` is the
handbook repository name (lowercase slug, usually matching `handbookId` /
git repo basename). Examples: repo `oh-my-docs` → Vercel `oh-my-docs-omd`;
repo `skills` → `skills-omd`. Adopt finds or creates that Vercel project
for env sync and deploy wiring—never a shared `oh-my-docs` Vercel app.

`projectRef` in the contract is the shared Supabase project’s ref after
resolution by name.

### Schema location (skill-scaffolded into each handbook repo)

On `--ssot supabase`, the skill embeds a **versioned migration tree** into
**that repository’s** docs app as static files (`docs/supabase/` from the
skill template; dogfood `apps/docs/supabase/`). The port applies pending
steps from that tree. A skill-only `references/` copy is insufficient
unless the same files are written into the consumer repo—the Vercel build
for that handbook must contain them.

Layout (contract):

```text
docs/supabase/
  migrations/
    core/                 # shared public registry + helpers
      001_….sql
    handbook/             # OMD baseline inside one pg_schema
      001_….sql
  migrate-public-to-handbook.sql   # legacy one-shot (optional)
```

Convenience snapshots such as `schema-1.1.sql` may exist for humans, but the
**runtime authority** is the ordered migration chain plus an applied-ledger.

### Ownership: core vs handbook-baseline vs operator DDL

The Oh My Docs skill is the authority for **Oh My Docs–owned** objects only.

| Class | Where | Owned by | Skill may |
|---|---|---|---|
| **Core** | `public.omd_handbooks`, `public.omd_ensure_handbook`, core ledger | Skill | Apply forward migrations on skill update / provision |
| **Handbook-baseline** | `{pg_schema}.omd_documents`, `{pg_schema}.omd_catalog_meta`, OMD-named RLS/policies | Skill (per `handbookId`) | Apply pending baseline migrations for the **selected** handbook only |
| **Operator / project DDL** | Any other tables, columns, functions, policies in the BYO project or inside `omd_h_*` | Handbook operators | **Never** `DROP` / `ALTER` / rename; ignore |

Operator-owned DDL is invisible to the skill migration planner. Product
fields that vary without DDL should prefer `frontmatter` jsonb so most
handbooks stay on a small set of baseline versions.

### Registry

`public.omd_handbooks` holds one row per handbook:

| Column | Meaning |
|---|---|
| `handbook_id` | Primary key; matches contract `handbookId` |
| `pg_schema` | Postgres schema name (`omd_h_…`) |
| `schema_version` | Last successfully applied **handbook-baseline** version |
| `created_at` / `updated_at` | Timestamps |

A separate **core** applied ledger (table or equivalent under `public`,
OMD-owned) records which core migration steps have run for the shared
project. Provision is idempotent on `handbook_id`. Creating a handbook
creates the Postgres schema and applies pending handbook-baseline steps for
the requested `schemaVersion` into that schema only.

### Content tables

Inside each handbook schema, OMD-owned baseline tables are:

- `omd_documents` — columns defined by the handbook-baseline migration set
- `omd_catalog_meta` — catalog registration shape defined by that set

Queries always qualify `{pg_schema}.omd_documents` (or set a transaction
`search_path` to that schema). Cross-schema joins for product features are
out of scope.

### Schema evolution (skill updates)

1. Skill releases ship **new forward migration files** under
   `migrations/core/` and/or `migrations/handbook/` and bump the packaged
   baseline `schemaVersion` when handbook-baseline changes.
2. After a skill update (or `adopt` / `sync` / explicit migrate), the port
   plans only **pending** steps from the ledger—never a full rewrite of
   live DDL.
3. **Core** pending steps apply once per Supabase project.
4. **Handbook-baseline** pending steps apply against **one** `handbookId`’s
   `pg_schema` when that handbook’s contract requests the new
   `schemaVersion` (or an explicit migrate for that id).
5. Sibling handbooks keep their previous `schema_version` until migrated.
6. Runtime `schema_drift` compares the selected handbook’s applied baseline
   (and pending core, if any) to the contract / skill package—not a
   project-wide forced upgrade.
7. Migration SQL for handbook-baseline must name only OMD-owned objects
   (tables `omd_*`, policies/functions with an `omd_` prefix or documented
   OMD names). Unknown objects in the same schema are left untouched.

There is no project-wide atomic upgrade of every `handbookId`.

### Legacy `1.0` layout

If `public.omd_documents` exists and `public.omd_handbooks` does not:

- Treat the project as a single handbook with `handbookId: "default"` and
  `pg_schema: public`.
- Reads/writes continue against `public.omd_*`.
- An explicit migrate creates a registry row, creates `omd_h_default` (or a
  chosen id), moves tables/data, and updates contracts.

Missing `handbookId` on a multi-handbook project (registry present) is an
error. On a legacy single-handbook project, omitted `handbookId` defaults to
`"default"`.

## Data and invariants

- One repository ↔ one `(projectRef, handbookId)`.
- `handbook_id` unique per Supabase project; `pg_schema` unique.
- No document row is visible to another handbook’s port operations.
- RLS remains enabled on content tables; policies are created inside each
  handbook schema. Registry writes require authenticated (or service) role;
  anon may read registry only if the docs app needs it to resolve
  `pg_schema` (optional—clients may derive `pg_schema` without reading the
  registry).
- Credentials never enter `.omd` JSON.

## Errors

| Code | When |
|---|---|
| `handbook_id_required` | Registry exists but contract omits `handbookId` |
| `handbook_id_invalid` | Slug fails format or is reserved |
| `handbook_id_conflict` | Registry row exists with a different `pg_schema` mapping |
| `schema_drift` | Selected handbook’s live schema ≠ contract `schemaVersion` |
| `migration_pending` | Skill package has core or handbook-baseline steps not yet applied |
| `migration_unsafe_object` | Planned SQL would touch a non-OMD-owned object name |
| `legacy_layout_ambiguous` | Both `public.omd_*` content and a conflicting registry entry |
| `project_inaccessible` | Host cannot access `projectRef` |

## Compatibility

- Single-handbook `schemaVersion` `1.0` projects keep working.
- `local` and `notion` contracts are unchanged.
- Does not introduce Oh My Docs–hosted tenancy.
- Operator-authored DDL coexists; skill migrations must not require removing
  it.

## Acceptance criteria

- Two `handbookId`s on one `projectRef` store disjoint document sets.
- Migrating handbook A’s schema leaves handbook B’s `schema_version` and
  `check` result unchanged.
- A skill update that adds a core migration applies it once without altering
  sibling handbook schemas.
- A handbook-baseline migration does not drop or alter a non-`omd_*` table
  that an operator added inside the same `pg_schema`.
- Legacy `public.omd_*` projects resolve as `handbookId: "default"`.
- Contract round-trip includes `handbookId` without secrets.
