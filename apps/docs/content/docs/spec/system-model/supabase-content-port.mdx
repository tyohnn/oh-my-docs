## Scope

Defines the Supabase adapter for the provider-neutral content port, the
provisioning manifest, document create/update behavior, validation, and how
Fumadocs loads remote MDX. There is no web editor. Multi-handbook tenancy
(registry + schema-per-handbook) is specified in SPEC-012 and enforced here.

## Interface

Adapters expose the same operations as the Notion port:

- `inspect`
- `planProvision`
- `planCreateDocument`
- `validateSnapshot`
- `recordResult`

The Node runtime plans and validates JSON manifests (SQL migrations, seed
rows, document upserts). The invoking skill checks host capability (Supabase
CLI login and/or Supabase MCP), executes operations, and returns a provider
snapshot. The runtime does not own OAuth or call Management APIs with hidden
credentials.

## Behavior

### Provision (`adopt --ssot supabase`)

1. Resolve host login / project access capability blockers (Supabase MCP/CLI;
   Vercel MCP when env sync is needed).
2. **Scaffold migrations into this handbook repo:** skill writes the
   versioned SQL tree under the docs app
   (`docs/supabase/migrations/{core,handbook}/` from the skill template).
   This is required so **this repo’s** Vercel deploy carries the schema
   contract the port will apply.
3. **Resolve shared Supabase project by name:** host lists Supabase projects
   and selects `name === "oh-my-docs"` (database name—not a Vercel project).
   If absent, create with that name when allowed; otherwise fail with an
   actionable free-plan / permission blocker.
4. Resolve `handbookId` for **this repo** (explicit, repo-derived slug, or
   `"default"` for legacy single-handbook).
5. `planProvision` emits a deterministic, idempotent manifest:
   - ensure core migration ledger + `public.omd_handbooks` registry
   - `apply_pending_migrations` for **core** (once per project)
   - `CREATE SCHEMA` for this handbook when missing
   - `apply_pending_migrations` for **handbook-baseline** inside that
     schema only (OMD-owned `omd_*` objects; never operator DDL)
   - IA seed rows for catalog keys from the shared IA graph
   - `vercel.ensure_project`: find or create Vercel project named
     `{projectSlug}-omd` for this handbook repo
   - `vercel.sync_supabase_env`: ensure that `{projectSlug}-omd` project
     has Connect publishable vars (`NEXT_PUBLIC_SUPABASE_URL`,
     `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, …). Do **not** require
     `OMD_CONTENT_SSOT`. Do **not** target a shared oh-my-docs Vercel app.
6. Host applies the manifest; runtime `validateSnapshot` / `recordResult`
   update `.omd/state.json` and write `contentSource.supabase` (including
   `projectRef`, `handbookId`, `schemaVersion`) into the project contract.
7. Optional: smoke one deploy of **this** handbook’s GitHub→Vercel project.

This provision path is entered only for `--ssot supabase`. Other SSOT values
use their own adapters.

Re-running provision must not duplicate stable document or catalog keys, must
not migrate sibling handbooks, and must skip already-applied migration
steps. After a skill update that adds core or handbook-baseline files,
provision/sync plans only the new pending steps (SPEC-012 ownership rules).

### Create document (`omd new`)

`planCreateDocument` targets the catalog implied by kind (same destinations as
local/Notion IA write targets). The host upserts a `documents` row from the
MDX template and updates `catalog_meta.pages[]`.

### Check / sync

- `check` loads a Supabase snapshot and validates the planning graph,
  lifecycles, and catalog registration.
- `sync` refreshes managed structure metadata / markers; it does not invent a
  second content authority.

### Fumadocs remote loader

When the project contract has `ssot: supabase` (set because the user chose
Supabase at adopt), the docs app **reads** documents and catalog nav from the
linked `oh-my-docs` project at render time using Connect publishable URL/key
env vars only—never from git-tracked secrets in `.omd`, and never by
requiring a Vercel `OMD_CONTENT_SSOT` override. Generated local caches (for
example `.supabase-content`, `.source`) remain non-authoritative and must not
be the only serve path for supabase SSOT. Routes `/docs/*` and `/md/*` stay
available. If the contract is `local` or `notion`, this loader path is not
used.

#### Read model (ISR + on-demand revalidate)

Serving uses a **cached remote read**, not a one-shot build materialize:

1. **Fetch** handbook rows (`omd_documents`, `omd_catalog_meta`) over PostgREST
   with the handbook schema profile (`Accept-Profile`) when
   `handbookId` maps to a non-`public` schema.
2. **Compile** MDX on demand (Fumadocs MDX Remote / equivalent) with the same
   component set as the local loader path. Trusted agent/CLI content only.
3. **Cache** fetches and compiled page/tree payloads with Next.js cache tags
   (at least a handbook-wide tag and optional per-path tags) plus a TTL floor
   (`revalidate` / ISR) so cold traffic does not hit PostgREST on every
   request.
4. **Invalidate on write:** after a successful content-port mutation
   (`omd new`, upsert, catalog `pages[]` change), the host or docs app calls a
   secret-gated revalidate endpoint that runs `revalidateTag` /
   `revalidatePath` for `/docs` and `/md`. A Git merge or full Redeploy is
   **not** required for handbook body or nav freshness.
5. New document paths must be reachable without a prior
   `generateStaticParams` entry (`dynamicParams` allowed for supabase SSOT).

Build-time pull-to-disk may remain as an optional CI/offline aid; it is not
the production read contract for `ssot: supabase`.

## Data and invariants

- One repository ↔ one `(projectRef, handbookId)` for handbook content.
- Many repositories may share one `projectRef` with distinct `handbookId`s.
- Stable planning IDs (`PRD-…`, `US-…`, …) are primary keys in that
  handbook’s `omd_documents`.
- Catalog entries live in that handbook’s `omd_catalog_meta`, never as
  ad-hoc unstructured blobs outside the IA.
- Schema migrations follow SPEC-012 ownership: core once per project;
  handbook-baseline per selected `handbookId`; operator DDL untouched.
- `schema_drift` / `migration_pending` reflect that ledger, not a full dump
  rewrite.
- Idempotency keys and digests make retries safe.
- Web UI editing of bodies is out of scope; only port writes mutate content.

## Errors

| Code | Meaning |
|---|---|
| `supabase_login_required` | Host not logged in to Supabase |
| `vercel_login_required` | Vercel MCP/tool required for env sync but not authenticated |
| `capability_missing` | Neither CLI nor MCP can apply the manifest |
| `project_inaccessible` | Cannot create/link/read the project |
| `shared_project_missing` | No Supabase project named `oh-my-docs` and create blocked |
| `schema_drift` | Selected handbook schema does not match bundled `schemaVersion` |
| `handbook_id_required` | Multi-handbook project missing `handbookId` |
| `handbook_id_conflict` | Registry mapping disagrees with derived `pg_schema` |
| `mapping_conflict` | Snapshot contradicts expected stable keys |
| `partial_apply` | Manifest interrupted; retry from pending ops |

## Compatibility

- Does not change Notion MCP manifests or local filesystem adopt.
- Does not publish Supabase content into Git as a second SSOT.
- Provider migration from local/Notion is a separate plan.

## Acceptance criteria

- Adopt with `--ssot supabase` after host login yields schema + IA seed and a
  valid project contract including `handbookId`.
- Second provision is idempotent and does not alter sibling handbooks.
- `omd new` and `check` succeed against the selected handbook only.
- Fumadocs renders a provisioned document over `/docs` and `/md` without
  treating a local MDX tree as authoritative.
- After a content-port write, `/docs` and `/md` reflect the new body or nav
  once revalidation runs—without requiring a Git merge or full Redeploy.
- Two handbooks on one `projectRef` stay isolated across schema upgrades.
- No web editor surface is required or shipped for this port.
