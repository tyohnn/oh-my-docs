## Scope

Defines the Supabase adapter for the provider-neutral content port, the
provisioning manifest, document create/update behavior, validation, and how
Fumadocs loads remote MDX. There is no web editor. Multi-handbook tenancy
(registry + schema-per-handbook) is specified in SPEC-012 and enforced here.

## Interface

Adapters expose the same operations as the Notion port:

- `inspect`
- `planProvision`
- `planCreateDocument`
- `validateSnapshot`
- `recordResult`

The Node runtime plans and validates JSON manifests (SQL migrations, seed
rows, document upserts). The invoking skill checks host capability (Supabase
CLI login and/or Supabase MCP), executes operations, and returns a provider
snapshot. The runtime does not own OAuth or call Management APIs with hidden
credentials.

## Behavior

### Provision (`adopt --ssot supabase`)

1. Resolve host login / project access capability blockers (Supabase MCP/CLI;
   Vercel MCP when env sync is needed).
2. **Resolve shared project by name:** host lists Supabase projects and
   selects `name === "oh-my-docs"`. If absent, create with that name when
   allowed; otherwise fail with an actionable free-plan / permission blocker.
3. Resolve `handbookId` (explicit, repo-derived slug, or `"default"` for
   legacy single-handbook).
4. `planProvision` emits a deterministic, idempotent manifest:
   - ensure `public.omd_handbooks` registry (schema `1.1+`)
   - `CREATE SCHEMA` for the handbook when missing
   - apply SQL from the **docs app schema tree**
     (`apps/docs/supabase/` or scaffolded `docs/supabase/`) for
     `documents` / `catalog_meta` (+ RLS) **inside that schema only**
   - IA seed rows for catalog keys from the shared IA graph
   - `vercel.sync_supabase_env`: ensure the linked Vercel project has
     Connect publishable vars (`NEXT_PUBLIC_SUPABASE_URL`,
     `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and Connect-provided server
     twins). Do **not** require `OMD_CONTENT_SSOT`.
5. Host applies the manifest; runtime `validateSnapshot` / `recordResult`
   update `.omd/state.json` and write `contentSource.supabase` (including
   `projectRef`, `handbookId`, `schemaVersion`) into the project contract.
6. Optional: observe or trigger one GitHub→Vercel deployment and confirm
   `/docs` renders; ongoing CD stays on GitHub.

Re-running provision must not duplicate stable document or catalog keys, and
must not migrate sibling handbooks.

### Create document (`omd new`)

`planCreateDocument` targets the catalog implied by kind (same destinations as
local/Notion IA write targets). The host upserts a `documents` row from the
MDX template and updates `catalog_meta.pages[]`.

### Check / sync

- `check` loads a Supabase snapshot and validates the planning graph,
  lifecycles, and catalog registration.
- `sync` refreshes managed structure metadata / markers; it does not invent a
  second content authority.

### Fumadocs remote loader

The docs app **hardcodes** handbook SSOT to `supabase` in code (not via
`OMD_CONTENT_SSOT`). At build/runtime it materializes or reads documents and
catalog nav from the linked `oh-my-docs` project using Connect publishable
URL/key env vars only—never from git-tracked secrets in `.omd`. Generated
local caches (for example `.supabase-content`, `.source`) remain
non-authoritative. Routes `/docs/*` and `/md/*` stay available.

## Data and invariants

- One repository ↔ one `(projectRef, handbookId)` for handbook content.
- Many repositories may share one `projectRef` with distinct `handbookId`s.
- Stable planning IDs (`PRD-…`, `US-…`, …) are primary keys in that
  handbook’s `omd_documents`.
- Catalog entries live in that handbook’s `omd_catalog_meta`, never as
  ad-hoc unstructured blobs outside the IA.
- Schema migrations and `schema_drift` are scoped to the selected handbook’s
  Postgres schema (SPEC-012).
- Idempotency keys and digests make retries safe.
- Web UI editing of bodies is out of scope; only port writes mutate content.

## Errors

| Code | Meaning |
|---|---|
| `supabase_login_required` | Host not logged in to Supabase |
| `vercel_login_required` | Vercel MCP/tool required for env sync but not authenticated |
| `capability_missing` | Neither CLI nor MCP can apply the manifest |
| `project_inaccessible` | Cannot create/link/read the project |
| `shared_project_missing` | No Supabase project named `oh-my-docs` and create blocked |
| `schema_drift` | Selected handbook schema does not match bundled `schemaVersion` |
| `handbook_id_required` | Multi-handbook project missing `handbookId` |
| `handbook_id_conflict` | Registry mapping disagrees with derived `pg_schema` |
| `mapping_conflict` | Snapshot contradicts expected stable keys |
| `partial_apply` | Manifest interrupted; retry from pending ops |

## Compatibility

- Does not change Notion MCP manifests or local filesystem adopt.
- Does not publish Supabase content into Git as a second SSOT.
- Provider migration from local/Notion is a separate plan.

## Acceptance criteria

- Adopt with `--ssot supabase` after host login yields schema + IA seed and a
  valid project contract including `handbookId`.
- Second provision is idempotent and does not alter sibling handbooks.
- `omd new` and `check` succeed against the selected handbook only.
- Fumadocs renders a provisioned document over `/docs` and `/md` without
  treating a local MDX tree as authoritative.
- Two handbooks on one `projectRef` stay isolated across schema upgrades.
- No web editor surface is required or shipped for this port.
