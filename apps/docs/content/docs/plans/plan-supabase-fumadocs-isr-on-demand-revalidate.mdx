## Scope

Narrow the `ssot: supabase` Fumadocs serve path to the SPEC-011 read model:

- Runtime PostgREST reads (handbook schema profile aware)
- On-demand MDX compile (`@fumadocs/mdx-remote` or equivalent)
- Next.js cache tags + TTL floor (ISR)
- Secret-gated on-demand revalidate after content-port writes
- `/docs` and `/md` stay in sync; new paths work without a prior static
  params entry

Keep `ssot: local` on the existing fumadocs-mdx filesystem collection.
Build-time `pull-supabase-content` may remain optional for CI/offline; it is
not the production authority path.

Out of scope: web editor, every-request `cache: 'no-store'`, Deploy Hook as
the only publish mechanism, search-index redesign, Notion runtime reads.

## Implementation sequence

1. Unify schema-aware REST helpers used by scripts and the docs app
   (`Accept-Profile` / `handbookId` → `omd_h_*`).
2. Add a Supabase → Fumadocs source (documents + catalog/IA page tree) with
   tagged `fetch` cache.
3. Branch `apps/docs` page/layout/`/md` for supabase SSOT: compile with MDX
   Remote, allow `dynamicParams`, share components with the local path.
4. Add `POST /api/revalidate` (or equivalent) gated by a non-git secret
   (`OMD_REVALIDATE_SECRET`); invalidate handbook tags and `/docs`+`/md`
   paths (`revalidateTag(..., { expire: 0 })` for webhook immediacy).
5. After successful content-port upserts, call the revalidate endpoint when
   the docs base URL + secret are configured (best-effort; document blocker
   when unset).
6. Document env keys in `.env.example`; keep publishable keys only for reads.
7. Tests: REST helper/schema headers, cache-tag naming, revalidate auth
   rejection; mocked compile path where feasible.

## Verification

- With Connect env + supabase contract: change a row (or `omd new`), call
  revalidate, confirm `/docs` and `/md` show the update without Redeploy.
- Local SSOT docs app still builds from filesystem MDX.
- `pnpm --filter @oh-my-docs/docs test`, `pnpm check:planning`,
  `pnpm typecheck` (docs) pass.
- Revalidate without secret → 401/403; no secret values in logs.

## Migration and compatibility

- Existing build-pull scripts stay available but non-authoritative.
- Projects on `local` / `notion` unchanged.
- Dogfood may enable supabase serve once secrets + revalidate URL exist.

## Risks and rollback

- Runtime MDX compile cost — mitigate with tags + TTL; avoid no-store default.
- mdx-remote limits (no MDX import/export) — handbook templates already use
  injected components.
- Stale nav if only body tags invalidate — always invalidate handbook-wide
  tree tags on catalog `pages[]` changes.
- Rollback: feature-flag serve path on `ssot === 'supabase'`; fall back to
  previous build-pull SSG.

## Completion criteria

- SPEC-011 remote-loader observables (cached remote read + write-triggered
  revalidate) hold on a real or CI Supabase project.
- US-009 freshness acceptance criterion is met.
- Plan stage moves to `done` after verification.
