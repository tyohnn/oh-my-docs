## Scope

Deliver multi-handbook BYO Supabase tenancy plus per-handbook deploy wiring:

- Shared **Supabase** project discovery by name `oh-my-docs` (not a Vercel
  project)
- **Per handbook repo** Vercel deployment named `{projectSlug}-omd`; skill
  does not assume one oh-my-docs Vercel app
- On `--ssot supabase`, skill **scaffolds a migration tree into that repo**
  (`docs/supabase/migrations/{core,handbook}/`; dogfood
  `apps/docs/supabase/`)
- Contract/state fields for `handbookId` (and legacy defaulting)
- Registry + schema-per-handbook baseline (`schemaVersion` `1.1`) with a
  **forward migration ledger** (core once per project; handbook-baseline per
  `handbookId`)
- Skill updates apply **pending OMD-owned migrations only**; operator DDL in
  handbook schemas is never dropped or altered
- Content-port provision/create/check scoped to one handbook
- After `--ssot supabase`, contract records SSOT in `.omd` (no Vercel
  `OMD_CONTENT_SSOT`); `local` / `notion` unchanged
- Build/prepare pulls when contract is supabase **and** Connect env exist
- Adopt host ops `vercel.ensure_project` + `vercel.sync_supabase_env` for
  Vercel project **`{projectSlug}-omd`** (CLI/REST or Connect)
- Per-repo GitHub → Vercel CD; optional smoke of that handbook only
- Idempotent migrate path from legacy `public.omd_*`
- Tests for isolation, scaffold-in-repo SQL, discovery, legacy default,
  pending-migration planning, and non-touch of unknown objects

Out of scope: OMD-hosted multi-tenant cloud, single Vercel for all
handbooks, cross-handbook UI, merge of two Supabase projects, skill-owned
CD, web editor, migrating operator-authored tables.

## Implementation sequence

1. Add skill template migration tree
   `docs/supabase/migrations/{core,handbook}/` (baseline `1.1`) plus
   optional human snapshot SQL; dogfood `apps/docs/supabase/`; adopt
   copies/scaffolds them into the target repo on `--ssot supabase`. Port
   loads SQL from the **repo docs path**, not only skill `references/`.
2. Introduce an OMD-owned **applied migration ledger** (core + per-handbook
   baseline). `planProvision` / skill-update sync emit only **pending**
   steps; never rewrite unknown objects.
3. Docs app reads SSOT from `.omd`. When `ssot: supabase`,
   `prepare-content` / `build-with-content` pulls if Connect env present.
   No `OMD_CONTENT_SSOT`. Leave `local` / `notion` unchanged.
4. Extend contract with `handbookId`; derive `pgSchema`; update normalize /
   adopt helpers.
5. `planProvision`: `scaffold_docs_supabase_sql` →
   `resolve_project_by_name` (`oh-my-docs` Supabase) →
   `apply_pending_migrations` (core, then this handbook’s baseline) →
   upsert registry → seed catalogs → `vercel.ensure_project`
   (`{projectSlug}-omd`) → `vercel.sync_supabase_env` on that project.
6. Scope create/check/pull/Fumadocs to `{pg_schema}.omd_*`.
7. SKILL/AGENTS: host uses Supabase MCP for `oh-my-docs` DB; Vercel
   CLI/REST for **this** handbook’s project env; document blockers and
   migration ownership (core vs handbook-baseline vs operator DDL).
8. Tests: adopt writes migration tree into throwaway repo; two handbooks
   isolation; migrate A without touching B; skill-update applies new core
   step once; handbook-baseline leaves a planted non-`omd_*` table alone;
   no `OMD_CONTENT_SSOT`; local adopt unchanged; secret rejection
   unchanged.

## Verification

- Unit: provision plan includes scaffold migrations + resolve-by-name +
  pending-migration ops + per-repo vercel env op; distinct schemas for two
  `handbookId`s; unknown-object safety.
- Manual: adopt throwaway handbook repo → `docs/supabase/migrations/`
  present in git → shared Supabase `oh-my-docs` → Vercel
  `{projectSlug}-omd` has Connect env → deploy serves `/docs`.
- Second handbook repo: own Vercel `{otherSlug}-omd`, same Supabase,
  isolated schema; skill bump that adds a core migration does not change
  B’s `schema_version`.
- `pnpm check:planning` and skill runtime tests pass.

## Migration and compatibility

- Default: no break for current `public.omd_*` adopters (`handbookId`
  defaults to `default`).
- Opt-in migrate moves data into `omd_h_<id>` and writes `handbookId`.
- Orgs with differently named projects rename or create `oh-my-docs` once;
  adopt does not guess other names.
- `schemaVersion` `1.0` remains valid for unmigrated projects; new multi-
  handbook adopts use `1.1+`.
- Existing snapshot SQL (`schema-1.1.sql`) may remain as a convenience
  bootstrap; new changes after that land only as ordered migration files.

## Risks and rollback

| Risk | Mitigation |
|---|---|
| Accidental cross-schema query | Qualify all SQL; tests for missing schema filter |
| Skill update wipes operator DDL | OMD-owned name allowlist; `migration_unsafe_object` |
| Free-plan cannot create `oh-my-docs` | Clear `shared_project_missing` + pause/restore guidance |
| Vercel MCP unauthenticated in agent host | `vercel_login_required` blocker; Connect already-linked is OK |
| SQL drift skill vs docs app | Single canonical path under docs app; CI path check |
| Operators confuse Supabase project with handbook | `inspect` shows name, `projectRef`, and `handbookId` |

Rollback: leave legacy `public` layout untouched until migrate succeeds;
failed adopt retries from pending ops without deleting sibling handbooks
or operator objects.
