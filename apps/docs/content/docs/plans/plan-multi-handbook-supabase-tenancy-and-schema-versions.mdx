## Scope

Deliver multi-handbook BYO Supabase tenancy plus zero-friction adopt wiring:

- Shared Supabase project discovery by name `oh-my-docs` (MCP list / create)
- Contract/state fields for `handbookId` (and legacy defaulting)
- Registry + schema-per-handbook SQL (`schemaVersion` `1.1`) living under
  **`apps/docs/supabase/`** (and template `docs/supabase/`)
- Content-port provision/create/check scoped to one handbook
- Docs app hardcodes SSOT `supabase` (no `OMD_CONTENT_SSOT` env)
- Build/prepare pulls content when Connect URL/key env exist
- Adopt host op `vercel.sync_supabase_env` via Vercel MCP/tool
- GitHub → Vercel remains CD; optional one-shot deploy smoke
- Idempotent migrate path from legacy `public.omd_*` → registry + dedicated
  schema
- Tests for isolation, independent schema upgrades, discovery, and legacy
  default

Out of scope: OMD-hosted multi-tenant cloud, cross-handbook UI, automatic
merge of two Supabase projects, skill-owned CD replacing GitHub, web editor.

## Implementation sequence

1. Move canonical SQL into `apps/docs/supabase/` (and template mirror); teach
   the skill port to load SQL from the docs app / template path; keep
   `references/` in sync or as a thin re-export.
2. Hardcode apps/docs `APPS_DOCS_CONTENT_SSOT = 'supabase'`; build
   `prepare-content` / `build-with-content` pulls when Connect env present
   (`NEXT_PUBLIC_SUPABASE_*` / `SUPABASE_*` publishable)—never
   `OMD_CONTENT_SSOT`.
3. Extend contract with `handbookId`; derive `pgSchema`; update normalize /
   adopt helpers.
4. Bundle schema `1.1` (registry + parameterized handbook DDL/RLS).
5. `planProvision`: op `resolve_project_by_name` (`oh-my-docs`) → upsert
   registry → `CREATE SCHEMA` → apply docs-app SQL → seed catalogs →
   `vercel.sync_supabase_env`.
6. Scope create/check/pull/Fumadocs to `{pg_schema}.omd_*`.
7. SKILL/AGENTS: host must use Supabase MCP to resolve `oh-my-docs`, Vercel
   MCP to sync env; document auth blockers (`vercel_login_required`,
   `shared_project_missing`).
8. Tests: discovery name match; two handbooks isolation; migrate A without
   touching B; build without `OMD_CONTENT_SSOT`; secret rejection unchanged.

## Verification

- Unit: provision plan includes resolve-by-name + vercel env op; distinct
  schemas for two `handbookId`s; SQL path resolves under docs app.
- Manual: adopt on a throwaway repo → finds/creates `oh-my-docs` → Vercel
  env present → GitHub deploy or one-shot deploy serves `/docs`.
- Second handbook on same project stays isolated across schema bump.
- `pnpm check:planning` and skill runtime tests pass.

## Migration and compatibility

- Default: no break for current `public.omd_*` adopters (`handbookId`
  defaults to `default`).
- Opt-in migrate moves data into `omd_h_<id>` and writes `handbookId`.
- Orgs with differently named projects rename or create `oh-my-docs` once;
  adopt does not guess other names.
- `schemaVersion` `1.0` remains valid for unmigrated projects; new multi-
  handbook adopts use `1.1+`.

## Risks and rollback

| Risk | Mitigation |
|---|---|
| Accidental cross-schema query | Qualify all SQL; tests for missing schema filter |
| Free-plan cannot create `oh-my-docs` | Clear `shared_project_missing` + pause/restore guidance |
| Vercel MCP unauthenticated in agent host | `vercel_login_required` blocker; Connect already-linked is OK |
| SQL drift skill vs docs app | Single canonical path under docs app; CI path check |
| Operators confuse Supabase project with handbook | `inspect` shows name, `projectRef`, and `handbookId` |

Rollback: leave legacy `public` layout untouched until migrate succeeds;
failed adopt retries from pending ops without deleting sibling handbooks.

## Completion criteria

- SPEC-012 and US-010 / US-011 acceptance criteria met in tests or documented
  manual smoke.
- Plan stage → `done` only after verification on a throwaway multi-handbook
  project with Vercel env sync (or Connect pre-linked).
- No web editor, OMD-hosted tenancy, or `OMD_CONTENT_SSOT` requirement.
