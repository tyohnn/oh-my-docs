## Scope

Deliver `contentSource.ssot: "supabase"` end to end:

- Contract/state schema for `projectRef` + `schemaVersion`
- Supabase content-port adapter (plan provision, create document, validate,
  record)
- Bundled declarative migrations + IA seed
- CLI/`needsSsot` + SKILL/AGENTS marker updates
- Fumadocs remote loader for `/docs` and `/md`
- Tests for contract round-trip, idempotent provision planning, and loader
  wiring

Out of scope: web editor, OMD-hosted multi-tenant DB, automatic
local/Notion→Supabase migration, runtime-owned OAuth secrets.

## Implementation sequence

1. Extend `project` / `state` JSON schemas and `normalizeContentSource` /
   `resolveContentSource` / `getContentAdapter` for `supabase`.
2. Add `runtime/content-sources/supabase.mjs` (+ adopt helper) implementing
   port operations and capability blockers (`supabase_login_required`, etc.).
3. Bundle versioned SQL migrations for `documents`, `catalog_meta`, and RLS;
   wire `schemaVersion` `1.0`.
4. Branch `omd adopt|new|check|sync` for Supabase manifests; update SKILL.md
   and managed `AGENTS.md` markers.
5. Add apps/docs remote source loader keyed by `.omd` contract + env publishable
   config; keep caches non-authoritative.
6. Add/extend runtime tests (`content-sources`, contract, adopt `needsSsot`
   options) and a docs read smoke path where feasible without a live project
   (mocked snapshot).

## Verification

- `node skills/oh-my-doc/scripts/omd.mjs inspect --json` recognizes supabase
  selection when present.
- Unit tests: provision plan idempotency, create-document targets, secret
  rejection, `needsSsot` includes `supabase`.
- With a throwaway linked project (manual/CI secret): adopt → `new` → `check`
  → Fumadocs renders the document.
- `pnpm check:planning` and `pnpm test` (skill runtime tests) pass.
- No web editor routes or UI added.

## Migration and compatibility

- Existing projects without `contentSource` remain `local`.
- `notion` and `local` adapters unchanged in behavior.
- Dogfood may stay on `local` until a separate migration is planned.

## Risks and rollback

- Host capability variance (CLI vs MCP) — mitigate with clear blockers and
  documented login steps.
- Schema drift on user projects — fail `check` on digest mismatch; avoid
  destructive auto-migrate.
- Rollback: leave adapter behind a contract value; projects on `local`/`notion`
  unaffected. Revert loader behind `ssot` branch.

## Completion criteria

- US-009 acceptance criteria are met for adopt, `new`, `check`, and Fumadocs

- SPEC-010 and SPEC-011 observables hold.
- Plan stage can move to `done` only after verification on a real or CI
  Supabase project smoke.
