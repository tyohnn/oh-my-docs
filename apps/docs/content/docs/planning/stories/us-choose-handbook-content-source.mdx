As a product team, I want to choose local MDX or Notion as the handbook SSOT
so that Oh My Docs fits our working environment without duplicate truth.

## Context

The selected provider changes where content operations happen, not the meaning
of PRDs, stories, Domain artifacts, specifications, ADRs, plans, or their
lifecycles.

## Acceptance criteria

- First greenfield adoption requires an explicit content-source selection
  (`local` or `notion`); agents must ask before calling `adopt`, and the
  runtime rejects greenfield adopt without `--ssot`.
- Existing projects without `contentSource` continue as `local`.
- The selection is persisted in `.omd/project.json`.
- After adopt, root `AGENTS.md` (managed marker) tells agents to read
  `.omd/project.json` `contentSource.ssot` and confirm whether the handbook
  SSOT is local docs or Notion before planning or content edits.
- Whenever the user discusses vision, roadmap, PRDs, stories, Domain, specs,
  ADRs, plans, or similar product intent, agents must check the selected SSOT
  for existing coverage and update or create the corresponding artifacts there
  so chat decisions do not become a second source of truth.
- `local` scaffolds the Fumadocs docs app and UI vocabulary under
  `packages/docs-ui` (legacy `packages/ui` still detected).
- `notion` requires an accessible Home root page and configured Notion MCP; it
  does not install local docs/UI packages.
- The supplied Notion root maps to `pages.home`; managed pages sit under a
  **데이터 원본** details toggle on Home (not a child page titled 데이터 원본).
- Notion provisioning creates the standard IA and one database per catalog.
- Repeated provisioning is idempotent.
- Skills route `inspect`, `adopt`, `new`, `check`, and `sync` through the
  selected provider.
- Missing MCP capability or root access produces an actionable blocker without
  partial writes outside the supplied root.

## Out of scope

- Keeping local MDX and Notion simultaneously authoritative.
- Automatic Notion-to-Fumadocs publishing.
