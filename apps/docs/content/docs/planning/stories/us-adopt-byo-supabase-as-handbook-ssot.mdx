As a product team, I want to store handbook MDX in my own Supabase project and
browse it with Fumadocs so that collaborators avoid Git content conflicts while
keeping the same templates and planning graph.

## Context

This story extends content-source selection. Structure metadata still comes from
the shared IA graph. Presentation stays Fumadocs. Editing stays agent/CLI-driven
through the content port—not a cloud UI.

## Acceptance criteria

- Greenfield `adopt` accepts `--ssot supabase` alongside `local` and `notion`.
- Before provision, the host must be logged into Supabase (CLI or MCP); missing
  capability yields an actionable blocker without partial authority writes.
- Adopt links an existing project or creates one when the host can, then applies
  a deterministic, idempotent schema migration and IA seed.
- `.omd/project.json` records `contentSource.ssot: "supabase"` plus non-secret
  `projectRef` and `schemaVersion`; secrets never appear in project or state.
- After adopt, managed `AGENTS.md` instructions tell agents to treat Supabase as
  the only handbook content SSOT when that value is selected.
- `omd new` creates catalog documents in Supabase (row + catalog registration)
  using the same templates and IDs as local.
- `omd check` validates the planning graph against the Supabase snapshot for
  `ssot: supabase`.
- The docs app loads documents and catalog nav from Supabase and exposes
  `/docs` and `/md`; a local MDX tree is not authoritative.
- After a content-port write (for example `omd new`), the handbook site shows
  the updated body and catalog nav via cached remote read + on-demand
  revalidation—without a Git merge or full Redeploy as the publish step.
- There is no product web editor for handbook bodies in this release.
- Local and Notion projects are unchanged.

## Out of scope

- In-browser editing of handbook MDX.
- Oh My Docs operating a shared multi-tenant database for all customers.
- Automatic migration of an existing local or Notion handbook into Supabase.
