As a developer who chose Supabase as the handbook SSOT for **this
repository**, I want the skill’s `omd adopt --ssot supabase` to (1) put the
handbook schema SQL into this repo’s docs app as static code, (2) attach
content to the shared Supabase project named `oh-my-docs`, and (3) wire
**this repo’s** Vercel project with Connect publishable env so GitHub
deploys of this handbook work—without a central “oh-my-docs” Vercel app or
an `OMD_CONTENT_SSOT` env.

## Context

SSOT selection remains an adopt-time choice (`local` | `notion` | `supabase`).
This story applies **only after** the user selects `supabase`.

Two different “oh-my-docs” ideas must stay separate:

| Thing | Role |
|---|---|
| Supabase project name `oh-my-docs` | Shared BYO database for many handbooks |
| Handbook git repo + its Vercel project | One deployable docs app per handbook |

There is **no** single Vercel project named oh-my-docs that serves every
handbook. Each handbook repo has its own Vercel deployment. The skill must
therefore **scaffold/copy schema SQL into that repo** so the deployed docs
app and the provisioned Postgres shape stay aligned.

## Acceptance criteria

- This flow runs only when adopt is invoked with `--ssot supabase` (or an
  equivalent moderated choice). `local` / `notion` adopts are unchanged.
- The skill writes declarative schema SQL **into this repository’s docs app
  tree** as static files (for example `docs/supabase/*.sql` from the skill
  template). Provision applies that SQL; the files remain in the repo for
  the handbook’s Vercel build/runtime contract.
- Host skill uses Supabase MCP (or CLI) to **list projects** and select the
  one whose name is exactly `oh-my-docs` (Supabase display name—not a
  Vercel project name).
- If none exists and the host can create projects, provision creates a
  Supabase project named `oh-my-docs`; if creation is blocked, adopt fails
  with an actionable blocker.
- Adopt writes `.omd/project.json` with `ssot: supabase`, the resolved
  `projectRef`, `handbookId` (this repo), and `schemaVersion`. No tokens.
  Operators do not set `OMD_CONTENT_SSOT` on Vercel.
- Host skill syncs publishable env onto **this handbook repo’s linked
  Vercel project** (`NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, …)—not onto a shared oh-my-docs
  Vercel app.
- Ongoing deploys are that repo’s GitHub → its Vercel project; adopt may
  smoke one initial deployment of **this** handbook.
- Re-running adopt is idempotent for the same repo/`handbookId`.

## Out of scope

- A single Vercel deployment that hosts every handbook.
- Storing `service_role` / secret keys in the repo or `.omd`.
- Replacing per-repo GitHub→Vercel CD with a skill-owned CD system.
- Oh My Docs hosting the shared database for every customer.
