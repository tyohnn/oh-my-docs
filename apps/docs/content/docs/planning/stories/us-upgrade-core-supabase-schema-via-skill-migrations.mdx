As a team that updates the Oh My Docs skill, I want core Supabase schema
changes to apply through a versioned migration chain so that every handbook
sharing `oh-my-docs` stays compatible, while DDL I added inside my own
handbook schema is never rewritten or dropped by the skill.

## Context

The skill is the authority for the **Oh My Docs platform schema** in a BYO
Supabase project (registry, ensure-handbook helpers, baseline
`omd_documents` / `omd_catalog_meta` shape and OMD RLS). Individual handbooks
may also carry operator-owned extensions. Schema-per-handbook isolation
(US-010) already prevents forcing every handbook onto one version; this story
adds ownership boundaries for what a skill update may migrate.

## Acceptance criteria

- Skill packages a forward-only **migration chain** (not a single rewrite
  dump) for Oh My Docs–owned objects, scaffolded into each supabase-adopted
  handbook repo under `docs/supabase/` (dogfood `apps/docs/supabase/`).
- Migrations are classified as **core** (shared `public` registry / helpers)
  or **handbook-baseline** (OMD tables/policies inside one `pg_schema`).
- Applying a skill update plans only **pending** migration steps against the
  linked project; already-applied steps are skipped (idempotent ledger).
- Core migrations never modify objects inside a handbook `omd_h_*` schema
  except through the handbook-baseline path for the **selected**
  `handbookId`.
- Handbook-baseline migrations touch only OMD-owned names
  (`omd_documents`, `omd_catalog_meta`, OMD-named policies/functions). They
  do not `DROP`/`ALTER` unknown tables, columns, or policies in that schema.
- Sibling handbooks keep their previous `schema_version` until that
  handbook’s contract opts into the new baseline version.
- `check` / `schema_drift` report pending core vs handbook-baseline steps
  without inventing a second SSOT.
- Secrets never enter `.omd` JSON.

## Out of scope

- Migrating or deleting operator-authored tables/columns inside a handbook
  schema.
- Automatic forced upgrade of every `handbookId` in the project.
- Merging two Supabase projects or rewriting non-OMD app schemas in the same
  BYO project.
