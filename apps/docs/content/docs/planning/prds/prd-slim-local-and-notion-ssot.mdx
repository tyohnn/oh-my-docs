## Problem

Three content sources plus Supabase remote serve, ISR, and Vercel revalidate
made documentation setup feel heavier than the product outcome. Humans track
work lightly; agents need durable catalogs—not a second full Notion handbook
chrome or a BYO database SSOT.

## Outcome

- Adoption offers **`local`** or **`notion`** only.
- **Local**: Git-tracked MDX with the existing Fumadocs handbook IA.
- **Notion**: user-supplied Home root; provision **inline catalog databases**
  only (each catalog index page embeds a DB; a row is a document). No Vision,
  Start here, or Workflow pages in Notion.
- Supabase handbook SSOT, remote Fumadocs loaders, and Vercel
  deploy/revalidate content-port features are **removed**.

## Goals

- One authoritative content source per repo (`local` | `notion`).
- Notion stays a lightweight index of ADR / Data model / API spec / Plans /
  PRDs / Stories (and sibling catalogs)—not a mirror of local section prose.
- Agents own Notion MCP and local file writes; users are not asked to run
  setup terminals for deleted Supabase/revalidate flows.
- Existing local Fumadocs behavior remains the default migration target for
  dogfood.

## Non-goals

- Bidirectional local ↔ Notion sync.
- Rendering Notion through Fumadocs.
- Keeping BYO Supabase as a content SSOT.
- Productized Vercel project provisioning or cache-bust webhooks.

## Success measures

- Greenfield adopt rejects `--ssot supabase`.
- Notion adopt creates Home + inline catalog DBs without Vision/Workflow pages.
- Docs app no longer branches on Supabase remote SSOT or `/api/revalidate`.
- `PRD-byo-supabase-*` outcomes are closed as superseded by this PRD.
