## Problem

Oh My Docs currently assumes every adopted repository stores handbook content
as local MDX. Some teams already work in Notion and need lightweight catalog
indexes without maintaining a second authoritative MDX copy.

## Outcome

During adoption, a team selects exactly one content source:

- `local`: Git-tracked MDX rendered by Fumadocs (full handbook IA)
- `notion`: a user-supplied Notion Home whose **inline catalog databases**
  are provisioned and operated through a host Notion MCP (slim IA; no Vision /
  Workflow chrome — see `PRD-008` / `ADR-008`)

The selection and non-secret provider identity live in `.omd/project.json`.
All skill operations route through the selected content port.

## Goals

- Preserve one authoritative content source per repository.
- Provision the default Oh My Docs IA beneath an approved Notion root.
- Use one Notion database per index-only catalog and preserve planning graph
  relations.
- Make provisioning deterministic, retryable, and idempotent.
- Keep credentials in the MCP host; never write them to the repository.
- Preserve existing local behavior and compatibility.

## Non-goals

- Bidirectional local/Notion synchronization.
- Rendering Notion content through Fumadocs in v1.
- Copying dogfood content into adopter workspaces.
- Treating MCP as a hidden network dependency of the Node runtime.
- Destructive deletion of user-authored Notion content.

Supabase as a third SSOT was explored under PRD-006 / PRD-007 and is
**withdrawn** by `PRD-slim-local-and-notion-ssot` (PRD-008) and `ADR-008`.

## Included stories

- `US-choose-handbook-content-source`

## Success measures

- A greenfield user can select `notion`, supply a root page, and receive the
  full default IA and typed catalog databases.
- Running provisioning twice creates no duplicate pages or databases.
- `new` and `check` operate against the configured provider.
- Existing `.omd` projects without a content-source field continue as `local`.
