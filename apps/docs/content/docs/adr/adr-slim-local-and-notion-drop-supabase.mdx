## Context

Supabase SSOT, revalidate/deploy ops, and the docs-first planning/development
gates added ceremony without matching how the product is used. Soft
deprecation and migration shims would keep the same weight.

## Decision

1. **SSOT is only `local` | `notion`.** Delete the Supabase content port,
   schemas, remote loaders, and related handbook catalog entries. No
   compatibility mode for `ssot: supabase`.
2. **`local`** keeps the full Fumadocs MDX handbook.
3. **`notion`** is one Home page with stacked inline catalog DBs only (no
   child catalog pages, no sidebar chrome, no Vision / Workflow pages).
4. **Delete** revalidate/deploy product surface (`OMD_REVALIDATE_*`,
   `/api/revalidate`, notify helpers, vercel content-port ops).
5. **Delete** the planning/development gates entirely:
   - Delete `check:docs-first` (not a no-op).
   - Delete `Plan:` / ready-plan-on-base requirements from agents and CI.
   - No “optional gate” or warnings-only mode.
6. **No soft migration.** Cut over dogfood to `local` (or `notion`) and remove
   dead code/docs in the same implementation. Do not keep dual-read paths,
   retired stubs, or export tooling for Supabase rows.

ADR-005 still means one SSOT; the set is `local` | `notion`.

## Consequences

- Existing `ssot: supabase` contracts are invalid; fix by switching `.omd` and
  deleting Supabase-only code — not by a long migration window.
- Handbook catalogs may still exist as ordinary docs; they are not a merge
  system.

## Rejected alternatives

- Warnings-only or no-op `check:docs-first`
- Keep superseded Supabase docs/code “for history” in-tree
- Soft dual-run of remote Supabase + local MDX
